# Research: Agent Loop & Orchestration Architecture

Date: 2026-07-12

`docs/research/prior-art.md` and `docs/research/anthropic-computer-use.md` already cover perception/grounding (UFO's hybrid UIA+vision, OmniParser, SoM prompting, OSWorld's grounding-is-the-hard-part finding) and the basic Anthropic tool-use loop shape. This note goes one level deeper on a narrower question: how do real computer-use systems structure the **control loop itself** — verifying an action worked, recovering from a stuck/failed action, deciding "done," and (for some) gating risky actions on a human. It's written to directly inform the `decide` and `act` nodes of the Phase 2 LangGraph orchestrator (`docs/decisions/0004-langgraph-orchestrator.md`), prompted by the 2026-07-10 Phase 1 incident (`docs/journal.md`): a `click` "succeeded" — no exception — while actually missing its target, and the follow-up `type` went to the wrong place. "No exception" and "had the intended effect" are different claims, and every system below has to answer the same question we're stuck on.

## Anthropic's `computer-use-demo` (deeper pass — control flow, not tool schema)

Sources: https://github.com/anthropics/claude-quickstarts/blob/main/computer-use-demo/computer_use_demo/loop.py, https://platform.claude.com/docs/en/agents-and-tools/tool-use/computer-use-tool

- **No verification layer exists in the harness code at all.** The `sampling_loop` function is mechanical: call the model, execute whatever tool calls come back, append the `tool_result` (screenshot included), repeat. There is no code path that compares before/after state or flags "this click probably missed." Verification, to the extent it happens, is 100% delegated to the model noticing its own screenshot looks wrong on the *next* turn.
- **No retry logic in the harness.** The only retry present is `Anthropic(api_key=api_key, max_retries=4)` — that's HTTP-transport retry (rate limits, transient network errors), not action-outcome retry. A failed/wrong action is not distinguished from a successful one by the loop; both just become the next `tool_result` and the model decides what to do next.
- **No max-iteration cap in the reference `while True:` loop.** The docs' own prompting-best-practices explicitly compensate for the missing harness-level verification by pushing it into the system prompt: *"prompt Claude to screenshot + explicitly evaluate outcome after each step before moving on"* — i.e., self-verification is a prompting convention, not a structural guarantee.
- **Task-done detection is purely the absence of further tool calls.** `if not tool_result_content: return messages` — the loop ends when the model's response contains no `tool_use` block. There is no separate "is the goal actually satisfied" check anywhere in the harness.
- **Takeaway for us**: this confirms the incident we hit isn't a bug specific to our code — it's the default failure mode of the entire "trust the model to notice" pattern Anthropic's own reference implementation uses. Every other system below adds *some* structural mechanism precisely because this default isn't good enough for anything beyond a demo. We should not copy the reference loop's verification story (there isn't one) even though we're copying its action vocabulary and error-result pattern.

## Microsoft UFO2 (control loop / state machine — arXiv 2504.14603)

Sources: https://arxiv.org/abs/2504.14603, https://arxiv.org/html/2504.14603v1, https://github.com/microsoft/UFO/blob/main/documents/docs/ufo2/overview.md

- **Explicit finite-state machines, not a bare loop.** Per the paper, HostAgent's control flow is a state machine with states `CONTINUE, ASSIGN, PENDING, FINISH, FAIL`; AppAgent's is `CONTINUE, PENDING, FINISH, FAIL`. "Done" is a *state the FSM transitions into*, not just "model stopped calling tools."
- **Re-observation after every action, structurally, not just prompted.** Both agents run an identical four-phase cycle each turn — data collection → LLM decision → action execution → memory update — and the paper's speculative-execution algorithm explicitly calls `UIA_GetContext()` to refresh state after each executed control, i.e. the harness itself re-queries ground truth (screenshot + UIA tree) after acting, rather than trusting the action call succeeded.
- **Explicit replan-on-failure, with a partial-success threshold.** The speculative multi-action algorithm includes logic along the lines of "if fewer than *k* of the planned actions actually executed, report partial progress and replan" — failure isn't silently absorbed, it triggers a distinct `Replan` path rather than blindly retrying the same action or blindly continuing the original plan.
- **Hard step caps, per level of the hierarchy**: 30 execution steps per AppAgent subtask; a separate cap on subtasks per HostAgent session (documented as 10 in the project's own config docs). Two independent guardrails at two levels, not one global counter.
- **"Done" is externally checked in their own eval, not just self-declared.** Their evaluation methodology (OSWorld-style) uses per-task verification scripts that check final system state, plus a separate LLM-based "Automated Task Evaluator" that reasons over the full session trace to label success/partial/failure — i.e. even UFO2's own benchmarking doesn't trust the agent's self-report of "finished" at face value.
- **Takeaway for us**: this is the strongest structural precedent we found for "verify by re-perceiving, not by trusting the call." UFO2's `Execute → refresh state → check → (continue | replan | fail)` shape maps almost directly onto what our `act` node should do, and its two-tier step caps (per-subtask and per-session) are a concrete pattern for `AgentState.step_count`.

## Simular AI's Agent S2 (arXiv 2504.00906)

Sources: https://arxiv.org/abs/2504.00906, https://arxiv.org/html/2504.00906v1, https://github.com/simular-ai/Agent-S

- **Manager/Worker split (planner/executor), not a single loop.** At each high-level step the Manager generates a plan (subgoals) from the instruction and current observation; the Worker takes the first subgoal and, at each low-level step, picks and executes actions via its own policy, delegating precise element localization to a separate set of "Grounding Experts" (the Mixture-of-Grounding piece, which is the perception-side finding our earlier note already touched on).
- **Explicit success/failure signal returned per subgoal.** The Worker concludes each subgoal with `SUCCESS` or `FAILURE` and returns control to the Manager — a structural checkpoint between execution and re-planning, though the paper's available text doesn't spell out the exact mechanism that decides SUCCESS vs. FAILURE (screenshot diff vs. model judgment); we could not confirm this detail from the parts of the paper we could fetch and are flagging that explicitly rather than guessing.
- **Replanning is continuous, not just triggered by outright failure.** "Proactive Hierarchical Planning": after each subgoal returns control, the Manager regenerates the *remaining* plan using the latest observation, not just the original static plan — so drift/partial-progress gets folded back in every cycle rather than only on hard failure.
- **"Adaptive Interaction" as an explicit retry-differently pattern**: the paper describes the agent retrying a stuck interaction with the *same* element or page using a *different* method (rather than repeating the identical failed action) as an observed behavior category — closer to "retry differently" than "retry same" or "abort."
- **Done is self-declared via an explicit action.** The action space includes a `done` action ("mark subtask as success") with no arguments — task completion is the Worker/agent asserting it, not an external check, as far as we could confirm from the paper text and README; no separate verifier module is documented for overall task completion (only the per-subgoal SUCCESS/FAILURE handoff described above).
- **Takeaway for us**: the Manager/Worker split is a heavier-weight architecture than our three-node graph needs right now (we don't have a fake Brain sophisticated enough to plan multi-step subgoals yet), but the *shape* — decide, act, return a structured outcome, let the higher level re-plan from fresh observation — is exactly the loop-back edge we already have in the LangGraph (`act` → `perceive` → `decide`). Worth revisiting once our Brain is real and multi-step planning becomes worthwhile.

## ByteDance UI-TARS (arXiv 2501.12326)

Sources: https://arxiv.org/abs/2501.12326, https://arxiv.org/html/2501.12326v1, https://github.com/bytedance/ui-tars

- **Reflection is trained into the model, not implemented as harness logic.** UI-TARS's "System-2 reasoning" and "reflection tuning" are a *training-data and fine-tuning* story: annotators label (a) error-correction pairs — mistakes in real agent traces plus the correct fix, and (b) post-reflection pairs — simulated recovery steps showing how to realign after an error. These get folded into training via DPO so the model *itself* learns to recognize and correct its own mistakes mid-trajectory, expressed as "Thought" tokens (task decomposition, milestone recognition, reflection) before each action.
- **This means UI-TARS's error recovery lives in the model weights, not in an external verifier or retry loop we could point to.** We could not find, in the README or the fetched paper sections, any description of a harness-level mechanism that independently detects a failed action and forces a retry/replan — the paper is explicit that recovery is something the model does as part of its own reasoning trace, learned from the DPO data.
- **Terminal actions are part of the model's own action vocabulary**: `Finished()` for task completion and `CallUser()` for "hand back to a human" when the agent can't proceed — both self-emitted by the model, same self-declare pattern as Agent S2's `done` action and Anthropic's "stop calling tools."
- **Step limits are a benchmark-harness artifact, not an architectural guardrail we could confirm**: e.g. OSWorld runs at "50 steps" / "15 steps" in their reported numbers, and long-horizon memory is bounded by keeping only the last N observations — but this reads as an evaluation-protocol constraint rather than a documented in-product safety cap.
- **Takeaway for us**: UI-TARS is the weakest source of *harness-level* architecture patterns here — its contribution is almost entirely "train the recovery behavior into the model" rather than "build the recovery behavior into the loop." That's not an option for our scripted/fake Brain today, but it's a useful reminder that once we plug in a real model Brain (per ADR-0002), some of the self-verification burden can shift from our `act`/`decide` node logic onto good prompting/model choice — it doesn't have to all be re-implemented as harness code.

## browser-use

Sources: https://github.com/browser-use/browser-use, https://github.com/browser-use/browser-use/issues/191, https://docs.browser-use.com/customize/agent/all-parameters

- **A structured per-step self-critique field, not free-form "did it work?" prose.** Every step's model output is required to include an `evaluation_previous_goal` field judging whether the *previous* action succeeded, alongside `next_goal` and (unless `flash_mode` is on) a `thinking` field — i.e. the self-verification step from Anthropic's prompting best-practices is made a **mandatory structured field** here rather than a soft prompt suggestion.
- **Concrete numeric guardrails**: `max_failures` (default 3) caps retries for steps that error; `max_actions_per_step` (default 4) caps how much the agent batches per turn (actions execute "until the page changes," i.e. it stops batching once it detects state changed); `final_response_after_failure` (default True) forces one last model call with whatever partial output exists once `max_failures` is hit, instead of just crashing or hanging silently.
- **A known, openly acknowledged gap that's directly relevant to us**: issue #191 documents the exact failure mode of trusting self-declared progress — an agent that opened the right page then scrolled 40+ times because the model kept deciding the task "wasn't done yet," and a separate case of inventing extra work after the real goal was already met. The maintainers' own diagnosis: *"the validator only runs at the end, instead of after every step."* Their proposed fix is per-step validation (optionally with multiple validators + majority vote) rather than a single end-of-run check.
- **Takeaway for us**: this is the clearest cautionary tale in this whole set of a **self-declared "done" with no independent check** going wrong in practice, from a framework with far more real-world usage than the academic systems above. It directly argues for our `decide`/`act` loop not relying solely on the Brain saying "I'm done" — some cheap independent signal (unchanged screenshot/UI tree across N consecutive steps, a step budget, etc.) should be able to force a stop even if the Brain keeps insisting otherwise.

## OpenAI Computer-Using Agent (CUA) / Operator

Sources: https://developers.openai.com/api/docs/guides/tools-computer-use, https://openai.com/index/operator-system-card/, https://community.openai.com/t/computer-tool-has-unacknowledged-safety-check/1147615

- **Loop shape matches Anthropic's**: send a task, the model returns `computer_call` actions, your harness executes them and captures a fresh screenshot, you send it back as `computer_call_output` keyed to the same `call_id`, repeat. Completion is detected the same way as Anthropic's reference loop: *"When the response no longer contains a `computer_call`, read the remaining output items as the model's final answer."* No screenshot-diffing or independent outcome verification is documented in the guide itself — same gap as Anthropic's harness.
- **No documented retry/max-iteration convention from OpenAI** beyond an example harness parameter (`max_steps: number = 50`) shown in a sample, not a platform guarantee.
- **The one genuinely distinct mechanism: a structural, blocking safety-check gate for risky actions**, independent of task-completion logic entirely. The API can return `pending_safety_checks` — entries with a machine-readable `code` (e.g. `malicious_instructions`) and a human-readable message (e.g. *"We've detected instructions that may cause your application to perform unauthorized actions"*) attached to a `computer_call`. Per a live developer-support thread, an unacknowledged check blocks the next call outright with an HTTP 400 (`"Computer tool has unacknowledged safety check for [...]"`) until the caller explicitly passes it back via an `acknowledged_safety_checks` parameter — the loop cannot silently proceed past a flagged risky action.
- **Separately, the system card describes user-facing pause points** for consequential actions (purchases, sending messages, deleting persistent data) where Operator shows a summary and waits for explicit approval, and an automatic pause when the user goes inactive/navigates away during a sensitive task (e.g. login) — a "supervision required" gate, distinct from the API-level safety-check gate above.
- **Takeaway for us**: OpenAI's core loop has the identical verification gap as Anthropic's (nothing in the docs suggests otherwise, and we could not find evidence of built-in outcome-checking). Its one real architectural contribution here is the **safety check as a first-class, blocking object in the state** — not a prompt convention, an actual field the loop cannot silently step past without an explicit acknowledgment. That is a directly reusable pattern for our own risky-action confirmation feature (already on the roadmap per `anthropic-computer-use.md`'s security section) — model it as a real blocking state field, not a prompt instruction we hope the Brain honors.

## Summary: how this shapes our `decide` / `act` node design

1. **The exception-vs-effect gap is universal, not something we did wrong.** Neither Anthropic's nor OpenAI's reference harnesses verify outcomes at all — both fully delegate this to the model noticing on the next turn. UFO2 and browser-use are the two systems that actually build a structural check, and both do it the same way: **re-observe, then compare**, not "trust the return value." Our `act` node should follow UFO2's pattern explicitly: after executing an `Action`, call back into `perceive` (or a lightweight version of it) *before* returning control, and attach some notion of "did the observable state change the way this action implies it should" to the result — not just "pyautogui didn't raise." This is the direct fix for the 2026-07-10 incident: a `click` followed immediately by a `type` with no re-perceive in between is exactly the gap UFO2 and browser-use both close structurally.

2. **`AgentState` needs an explicit failure/retry counter, not just `step_count`.** Every system with real guardrails (UFO2's per-subtask/per-session step caps, browser-use's `max_failures=3` + forced final response, OpenAI's sample `max_steps`) treats "consecutive failures" and "total steps" as separate budgets. We should add something like `consecutive_failures: int` alongside `step_count` in `AgentState`, with a small cap (browser-use's default of 3 is a reasonable starting point) that routes to a distinct "give up and report" terminal state rather than looping forever or crashing — this is cheap to add now even against the scripted fake Brain.

3. **"Done" should not be a single signal, ever — not even later with a real Brain.** Every self-declare-only system we found a failure mode for (browser-use issue #191 is the clearest, concrete, in-production example) breaks in exactly the way our roadmap should anticipate: the model keeps deciding "not done yet" (endless scrolling) or invents extra unrequested work after the goal is actually met. Our current `Brain.decide()` contract (`ActionType.DONE` self-declared by the Brain) is fine as the *primary* signal — it matches Agent S2's `done` action and UI-TARS's `Finished()`, i.e. it's the industry-standard shape — but the orchestrator graph itself should have an independent circuit breaker that can force `END` regardless of what the Brain says: e.g. N consecutive steps with no meaningful screenshot/UI-tree change, or `step_count` hitting a hard ceiling. With today's scripted fake Brain this is low-stakes (it can't loop unpredictably), but the safeguard needs to exist in the graph *before* a real model Brain is plugged in in Phase 3, not retrofitted after the first time it loops.

4. **Keep the graph a flat perceive→decide→act loop for now; don't adopt Manager/Worker yet.** Agent S2's planner/executor split is the most sophisticated architecture surveyed, but it's solving a problem (multi-step subgoal planning, replanning from drift) that our scripted fake Brain doesn't have yet — introducing that complexity now would be premature relative to ADR-0004's stated approach of building one node at a time and understanding each before the next. Revisit this once a real planning-capable Brain makes single-shot `decide()` calls insufficient.

5. **Model the risky-action confirmation as a real blocking state field when we build it (later phase), not a prompt instruction.** OpenAI's `pending_safety_checks` / `acknowledged_safety_checks` pattern is the one concrete, reusable design here: a flagged action should produce a distinct state the graph can route on (e.g. a conditional edge to a `confirm` node or `END` awaiting human input) rather than relying on the Brain's own judgment to "be careful." Not urgent for the current `decide`/`act` build-out, but worth keeping the `Action` schema and graph shape open to adding this edge later rather than closing it off.
